# ITOPS 智能运维告警分析系统 - 产品需求文档

## Overview
- **Summary**：使用 Python 构建的 ITOPS（IT Operations Intelligence）系统。系统对接 Zabbix 监控平台查询监控数据并接收告警 Webhook；对接 Graylog、Loki、ELK 日志平台获取日志；接入 MiniMax、DeepSeek、豆包、通义千问等大模型，对告警结合监控趋势与日志进行溯源与根因分析，生成分析报告，并将精简结论与处理建议推送到飞书、企业微信群。配套 Vue3 单页 Web 界面，支持亮色/暗色/跟随系统主题、响应式布局与分级菜单。
- **Purpose**：将"告警接收 → 指标与日志上下文聚合 → AI 根因分析 → 报告沉淀 → IM 通知"链路自动化，缩短 MTTR，减少运维人员在多个平台间切换排查的成本。
- **Target Users**：运维工程师、SRE、值班人员（内部工具，单管理员账号使用）。

## Goals
- 稳定接收并留存 Zabbix 告警，支持去重与自动/手动两种 AI 分析触发方式。
- 统一封装 Zabbix 监控数据查询能力（主机、监控项、历史/趋势数据、告警事件）。
- 统一封装 Graylog、Loki、ELK 三类日志平台的查询能力，输出归一化日志结构。
- 提供可配置的多供应商大模型接入层（MiniMax、DeepSeek、豆包、通义千问），支持供应商与模型切换、失败降级。
- AI 分析必须同时引用"告警信息 + 指标趋势证据 + 日志证据"，产出结构化根因分析报告（根因、证据链、影响面、处置建议）。
- 分析报告可列表查看、详情查看、导出（Markdown）、重新分析。
- 精简后的分析结论与处理建议可通过飞书、企业微信群机器人 Webhook 自动或手动推送。
- Web 界面提供集成式工作台，支持亮/暗/跟随系统三态主题、全分辨率自适应、层级合理的分级菜单。
- Docker Compose 一键部署，真实环境凭据通过配置文件/环境变量注入。

## Non-Goals
- 不做多租户、多用户与细粒度 RBAC 权限体系（仅单管理员登录）。
- 不替代 Zabbix/日志平台本身的功能（不做监控项配置下发、日志采集 agent 管理）。
- 不做告警降噪编排引擎（复杂规则引擎、告警收敛、排班 oncall 不在本期范围）。
- 不做飞书/企业微信企业自建应用（仅群机器人 Webhook）。
- 不做移动端原生 App（响应式 Web 适配移动浏览器即可）。
- 不对大模型做本地私有化部署。

## Background & Context
- 工作目录 `/data/ops` 当前为空，为全新项目。
- 已确认技术选型：
  - 后端：Python 3.11+ / FastAPI（异步）
  - 前端：Vue 3 + Vite + Element Plus（SPA）
  - 存储：SQLite 默认零配置启动，通过配置切换 PostgreSQL（SQLAlchemy ORM 隔离）
  - 部署：Docker Compose（后端、前端 Nginx、可选 PostgreSQL）
  - 认证：单用户简单登录（JWT 会话，账号密码来自环境变量）
  - 通知：飞书、企业微信群机器人 Webhook（含签名校验）
  - 分析触发：收到告警后按配置自动触发 + 界面手动触发并存
  - 验证方式：用户提供真实 Zabbix / Graylog / Loki / ELK / 大模型环境联调；单元测试使用 Mock
- 用户偏好：集成式界面而非多页面跳转；中文界面。

## Functional Requirements

### 监控对接
- **FR-1 Zabbix 连接配置**：可在系统配置中维护 Zabbix Server URL、用户名/密码或 API Token、连接校验；凭据加密存储，不在接口明文返回。
- **FR-2 Zabbix 监控数据查询**：支持主机列表/搜索、按主机查询监控项（items）、查询监控项历史数据与趋势数据（指定时间窗口、返回时间序列）、查询当前问题/告警事件列表。
- **FR-3 告警接收**：提供 Zabbix Webhook 接收端点（`/api/v1/webhooks/zabbix`），兼容 Zabbix 官方 Webhook media type 常见 JSON 载荷（event_id、主机、触发器、级别、状态、时间、详情等），支持可选 Webhook Token 校验；异常载荷返回明确错误并记录原始报文。
- **FR-4 告警去重与状态**：按 Zabbix event_id 去重；同一事件恢复消息更新告警状态；告警生命周期状态至少包含：未恢复、已恢复、已分析、分析失败。

### 大模型接入
- **FR-5 多供应商接入**：支持 MiniMax、DeepSeek、豆包（火山方舟）、通义千问（DashScope）四家供应商，均通过其 OpenAI 兼容接口（或官方 Chat 接口）适配；可在界面配置 base_url、api_key、模型名、温度等参数并设置默认供应商。
- **FR-6 连接测试与降级**：界面上可对已配置供应商发起连通性测试；分析调用超时/失败时按预设备用供应商顺序重试一次，全部失败时分析任务标记失败并保留错误信息。

### 日志平台对接
- **FR-7 多平台配置**：支持 Graylog（REST API）、Loki（HTTP API / LogQL）、Elasticsearch（ELK，_search API）三类平台的地址、认证信息、默认索引/流/日志源的配置与连通性校验；可启用/停用平台。
- **FR-8 统一日志查询**：提供统一日志查询接口，入参为平台、时间范围、查询语句/关键词、主机名过滤、条数限制；返回归一化结构（时间戳、主机、来源、级别、消息原文），各平台 DSL 差异由后端适配。
- **FR-9 日志查询界面**：界面提供集成式日志查询台，可切换平台、选择时间范围、输入查询、分页/滚动查看结果。

### AI 分析
- **FR-10 分析上下文聚合**：分析时自动聚合：①告警详情；②告警主机相关监控项在告警前后时间窗口（默认前 30 分钟、后 10 分钟，可配置）的历史/趋势数据与统计特征（均值、峰值、变化率、突变点描述）；③同一时间窗口内该主机在各已启用日志平台上匹配到的相关日志（错误/异常关键词及上下文）。
- **FR-11 根因分析**：基于聚合上下文调用大模型进行溯源与根因分析，输出结构化结果：可能根因（含置信度排序）、证据链（必须关联具体指标数据点/日志条目）、影响范围、处置建议（可执行步骤）、预防建议；模型以 JSON 结构化输出，解析失败时有容错（重试或降级提取）。
- **FR-12 自动与手动触发**：收到新建告警后按开关配置自动入队分析；界面支持对任意告警手动发起分析与重新分析；分析在后台异步执行，界面可看到分析中/成功/失败状态。
- **FR-13 分析报告**：报告含原始告警、指标上下文摘要、日志证据摘要、结构化分析结论、使用的模型与耗时、时间戳；支持列表（按告警/时间/状态筛选）、详情、Markdown 导出。

### 通知
- **FR-14 渠道配置**：支持配置飞书与企业微信群机器人 Webhook 地址、加签密钥、启用开关，并提供"测试发送"按钮。
- **FR-15 通知推送**：分析成功后可按开关自动推送，或在报告详情手动推送；消息为精简富文本卡片：告警标题/级别/主机、根因结论（1~3 条）、关键证据简述、处置建议（精简步骤）、报告详情链接；两类平台消息格式各自适配（飞书 interactive 卡片 / 企业微信 markdown 或图文卡片）。

### Web 界面
- **FR-16 主题**：提供"跟随系统 / 亮色 / 暗色"三态切换；跟随系统时监听系统主题变化实时生效；选择持久化，刷新与重新登录后保持。
- **FR-17 响应式布局**：在 ≥1920、1440、1024、≤768（平板/手机宽度）分辨率下均可用：侧边栏可折叠、窄屏自动收起为抽屉、表格横向滚动/卡片化、图表自适应容器宽度。
- **FR-18 信息架构与菜单**：分级菜单层级清晰（建议两级，不超过三级），至少包含：总览仪表盘、告警中心（告警列表、分析报告）、监控数据（主机与指标）、日志查询、集成配置（Zabbix、大模型、日志平台、通知渠道）；界面为集成式工作台，告警详情页内可同屏查看指标趋势、相关日志、分析结论与通知状态，避免跨页面跳转。
- **FR-19 登录与会话**：未登录访问跳转登录页；登录后 JWT 会话有效期内免登录；支持退出登录。
- **FR-20 仪表盘**：总览页展示近 24 小时告警数量与级别分布、分析成功率、最新告警流、各集成平台连通状态。

### 非功能与部署
- **FR-21 配置与部署**：提供 `.env.example` 与 docker-compose.yml（后端服务、前端 Nginx 服务、可选 postgres 服务、数据卷）；`docker compose up -d` 可完成启动；提供初始化管理员账号与最小化配置指引。
- **FR-22 可观测与健壮性**：后端记录结构化日志；对外部平台调用设置超时、异常捕获与用户可读错误；凭据类字段接口返回时脱敏。

## Non-Functional Requirements
- **NFR-1 性能**：监控/日志查询接口（下游正常时）P95 响应 ≤ 3 秒；单次 AI 分析异步执行，不阻塞 Webhook 返回（Webhook 接收响应 ≤ 500ms）。
- **NFR-2 可靠性**：外部平台不可用时核心告警接收与入库不受影响；分析任务失败有明确失败原因，可重试。
- **NFR-3 安全**：所有业务接口除登录与 Zabbix Webhook（独立 Token）外均需 JWT；第三方平台凭据加密存储（密钥来自环境变量）；密码不以明文落库；Webhook 端点支持 Token 校验。
- **NFR-4 可维护性**：外部系统对接采用统一适配器接口（Zabbix 客户端、日志平台基类、LLM Provider 基类、通知渠道基类），新增供应商/平台不改动分析主流程。
- **NFR-5 可移植性**：仅通过配置即可在 SQLite 与 PostgreSQL 间切换；不写数据库方言专有 SQL。
- **NFR-6 质量**：后端核心逻辑（去重、上下文聚合、模型输出解析、消息渲染、签名）具备 Mock 单元测试，pytest 可一键运行；前端具备基本构建检查（`npm run build` 通过）。
- **NFR-7 兼容性**：前端兼容最新版 Chrome/Edge；后端兼容 Python 3.11+。

## Constraints
- **Technical**：Python 3.11+、FastAPI、SQLAlchemy、Vue3 + Vite + Element Plus + Pinia + Vue Router + ECharts；Zabbix 6.0/7.0 JSON-RPC API；LLM 调用走各家 OpenAI 兼容 HTTP 接口；日志平台走官方 HTTP API。
- **Business**：内部运维工具，单管理员使用；界面与文档使用中文。
- **Dependencies**：真实 Zabbix、Graylog、Loki/ELK、大模型 API Key 由用户在联调阶段提供；未提供前开发与单测使用 Mock 与配置占位，不得阻塞开发。

## Assumptions
- Zabbix 已配置媒体类型为 Webhook，可向本系统发送 JSON 告警报文；用户具备在 Zabbix 配置动作的能力。
- 大模型各供应商均提供有效 API Key 且账户可用。
- 日志平台中主机标识可与 Zabbix 主机名/可见名对应（映射不到时分析仍可执行，日志证据标注为空）。
- 部署主机可访问各外部平台地址。
- 指标与日志的历史保留时间窗口足以覆盖分析所需的告警前后时间范围。

## Acceptance Criteria

### AC-1：Zabbix 告警接收与去重
- **Type** `rule`
- **Given**：Zabbix 连接已配置，告警 Webhook 端点可用
- **When**：向 `/api/v1/webhooks/zabbix` 连续发送同一 event_id 的告警报文两次，再发送该事件的恢复报文
- **Then**：数据库只产生一条告警记录；其原始报文被留存；恢复报文到达后状态更新为"已恢复"
- **Pass Condition**：接口均返回 2xx；库中该 event_id 仅一条记录且最终状态为已恢复；恢复事件记录可查
- **Evidence**：接口请求/响应记录、数据库查询结果、自动化测试输出

### AC-2：Zabbix 监控数据查询
- **Type** `rule`
- **Given**：Zabbix 地址与凭据正确
- **When**：在界面/接口搜索主机、选择监控项并查询指定时间窗口的历史数据
- **Then**：返回主机列表、监控项列表及带时间戳的时间序列数据点
- **Pass Condition**：返回结构与真实 Zabbix `host.get/item.get/history.get` 数据一致，时间序列按时间升序；凭据错误时返回明确错误信息
- **Evidence**：真实环境联调截图/接口响应、pytest（Mock Zabbix 客户端）结果

### AC-3：多供应商大模型可配置、可测试、可切换
- **Type** `rule`
- **Given**：配置了至少两家供应商（如 DeepSeek、豆包）的 base_url、api_key、模型名
- **When**：分别点击连通性测试，并将默认供应商从 A 切换到 B
- **Then**：两家均返回测试成功/失败的明确结果；切换后新发起的分析实际调用 B 供应商；A 超时不可用时自动降级到 B
- **Pass Condition**：调用日志显示实际命中的供应商符合预期；api_key 在任何查询接口中脱敏
- **Evidence**：界面操作结果、后端调用日志、单元测试

### AC-4：三类日志平台统一查询
- **Type** `rule`
- **Given**：Graylog、Loki、ELK 中至少一类已启用且连接正常
- **When**：用统一查询接口指定平台、时间范围、主机与关键词进行查询
- **Then**：三类平台均返回归一化结构（timestamp/host/source/level/message），分页/限制条数生效；停用平台不可被查询并返回明确提示
- **Pass Condition**：归一化字段齐全且与平台原始日志内容对应；未启用平台返回明确业务错误
- **Evidence**：三平台真实或 Mock 联调结果、适配器单元测试

### AC-5：AI 根因分析证据完整性
- **Type** `rule`
- **Given**：一条真实 Zabbix 告警，相关主机有可查询的指标历史与日志数据，默认大模型可用
- **When**：对该告警发起分析（自动或手动）
- **Then**：后台依次完成指标窗口聚合、日志窗口聚合与大模型调用；产出结构化报告，包含根因（带置信度）、证据链、影响范围、处置建议；证据链中至少一条指标证据、一条日志证据（数据源确有数据时）
- **Pass Condition**：报告结构化字段完整可解析；证据条目可回溯到具体指标点/日志条目；分析过程与耗时被记录；数据为空时报告明确标注"无指标/日志证据"而非伪造
- **Evidence**：报告详情页与导出文件、后端日志、分析服务单元测试（含伪造 JSON 解析容错用例）

### AC-6：模型失败降级与失败可重试
- **Type** `rule`
- **Given**：配置了备用供应商
- **When**：默认供应商连续超时/鉴权失败
- **Then**：系统自动尝试备用供应商；均失败时告警置为"分析失败"并保留错误原因，界面可一键重新分析
- **Pass Condition**：调用顺序日志存在；失败状态与原因在界面可见；重试成功后生成报告
- **Evidence**：模拟失败的单元测试、界面操作结果

### AC-7：分析报告查看与导出
- **Type** `rule`
- **Given**：存在至少一份已完成的分析报告
- **When**：进入分析报告列表、打开详情、导出 Markdown
- **Then**：列表支持按时间/级别/状态筛选；详情展示告警、指标摘要、日志摘要、结论与模型元信息；导出的 .md 文件内容完整
- **Pass Condition**：筛选结果正确；导出文件可正常打开且包含各章节
- **Evidence**：界面验证、导出文件检查

### AC-8：飞书/企业微信通知
- **Type** `rule`
- **Given**：飞书、企业微信群机器人 Webhook 与加签密钥已配置
- **When**：点击"测试发送"，并对一份成功报告执行手动推送（自动推送开关另行验证）
- **Then**：两群均收到精简卡片消息，含告警标题/级别/主机、根因结论、关键证据、处置建议、报告链接；签名错误/地址错误时界面显示来自平台的明确错误
- **Pass Condition**：真实群内收到消息且内容要素齐全；自动开关开启时分析成功后自动送达；消息总长适配机器人限制（超长建议自动截断并附详情链接）
- **Evidence**：群消息截图、接口响应、签名算法单测

### AC-9：登录鉴权
- **Type** `rule`
- **Given**：管理员账号经环境变量初始化
- **When**：未登录访问任意业务页/API，以及使用正确、错误口令登录
- **Then**：未登录被拦截并跳转登录页/返回 401；错误口令被拒；正确口令登录获得 JWT 并可访问业务接口；退出后会话失效
- **Pass Condition**：上述四种行为均符合预期
- **Evidence**：接口测试与界面验证

### AC-10：主题三态切换
- **Type** `rule`
- **Given**：用户已登录
- **When**：在"跟随系统/亮色/暗色"间切换，并在跟随系统模式下改变操作系统主题；随后刷新页面
- **Then**：界面立即整体切换对应主题；跟随系统下随 OS 实时变化；刷新与重新登录后保持上次选择
- **Pass Condition**：Element Plus 明/暗样式覆盖全部组件（含菜单、卡片、表格、图表配色）；选择持久化
- **Evidence**：浏览器实际验证截图、localStorage/持久化检查

### AC-11：响应式自适应
- **Type** `rubric`
- **Dimension**：多分辨率可用性
- **Scale**：1-5
- **Anchors**：1 = 窄屏布局错乱、内容溢出不可用；3 = 主要页面可用但部分表格/图表需手动横向滚动或留白失衡；5 = 1920/1440/1024/390 宽度下侧边栏、表格、表单、图表、弹窗均自适应无横向页面级滚动且操作顺手
- **Pass Threshold**：>= 4
- **Evidence**：四种宽度下主要页面截图与人工检查

### AC-12：信息架构与集成式工作台
- **Type** `rubric`
- **Dimension**：菜单分级合理性与排查动线集成度
- **Scale**：1-5
- **Anchors**：1 = 菜单混乱、排查需在多个页面间来回跳转拼信息；3 = 菜单可找到各功能但告警、指标、日志、结论分散在多页；5 = 两级菜单清晰覆盖全部功能，告警详情同屏集成指标趋势图、相关日志、AI 结论与通知状态，完成一次根因排查无需离开该页
- **Pass Threshold**：>= 4
- **Evidence**：菜单结构走查、完成"查看一条告警并理解根因"任务的操作记录

### AC-13：一键部署与真实环境联调
- **Type** `rule`
- **Given**：一台装有 Docker/Compose 的干净 Linux 主机，用户提供真实 Zabbix/日志平台/大模型/机器人配置
- **When**：填写 .env 后执行 `docker compose up -d`
- **Then**：后端、前端（Nginx）、数据库正常启动；完成初始化后可在界面完成：连通性测试通过 → 收到真实或手动构造的 Zabbix 告警 → 生成真实 AI 分析报告 → 消息送达真实群
- **Pass Condition**：端到端主链路在真实环境全部打通；切换 PostgreSQL 仅需改配置重启
- **Evidence**：部署执行记录、各平台连通状态截图、端到端告警分析通知链路截图

### AC-14：测试与构建
